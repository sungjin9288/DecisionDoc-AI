# 공공 과업 문서 특화 설계 (2026-10-19)

- 승인 기록: `docs/future_feature_gates/public_sector_specialization.json` (approved 2026-10-19)
- 범위: 공공기관·공기업·지자체·국책과업의 제안서와 보고서를 RFP와 공식 기준에 대조하는 서버 없는 패키지(`app/public_sector/`)와 CLI(`scripts/publicdoc.py`), 세션용 skill
- 서버가 하지 않는 것: provider·G2B·외부 서비스 호출, 제출·입찰·평가 결과 판단

## 1. 왜 이 방향인가

사용자 판단(2026-10-19): Claude·Codex가 바로 만드는 문서는 이미 그대로 쓸 만하다. 이 프로젝트는 공공 과업에 특화해야 한다.

일반 생성이 반복해서 놓치는 것은 문장보다 **대조 작업**이다.

- RFP 요구사항 고유번호를 하나도 빠짐없이 다뤘는지
- 평가항목마다 어느 쪽에서 답하는지(조견표)
- 공문서 표기와 제출 조건을 지켰는지
- 제안서에서 약속한 내용이 이후 보고서와 맞는지

이 대조는 결정적 검사로 만들 수 있고, 원고를 누가 썼든(이 세션, DecisionDoc 작성 경로, DocumentOps) 같은 방식으로 적용된다.

## 2. 공식 기준 (조회일 2026-10-19)

**확인 수준과 사용 방식**

- **고정 규칙으로 쓴다:** 요구사항 분류 11종(S5), 항목 기호 순서·날짜·시각·금액·"끝" 표기(S1, S2), 조달청 집행 건의 PDF·용량·별도 파일·조견표(S9), 사업수행계획서 16개 목차(S7)
- **관행으로만 쓴다:** SFR·PER 같은 세 글자 약어. 공식 원문에서 찾지 못해 분류 추정에만 쓰고, 고유번호 접두어는 RFP에서 읽는다.
- **경고로만 쓴다:** 2타 들여쓰기, 항목 하나일 때 기호 생략. 근거가 2012년 편람뿐이다.
- **RFP에서 읽는다:** 쪽수·글꼴·요약본, 블라인드 조건(공식 고시에서 찾지 못함), 기술·가격 배점과 협상적격 기준(특히 지자체), 중간·완료보고서 목차, 정책연구 보고서 구성
- **적용 범위:** 공문서 표기 규칙의 법적 의무는 행정기관이 작성하는 문서다. 민간이 제출하는 제안서·보고서에는 권고로 적용한다(추론, 2단계에서 경고 수준으로 구분).

## 4. 1단계 설계

| 구성 | 파일 | 하는 일 |
|---|---|---|
| RFP 조건 카드 | `app/public_sector/models.py` | `RfpProfile`(strict, 미지정 필드 거부). 요구사항, 평가항목(배점, 정량·정성, 답하는 목차), 제출 조건, 배점. 모르는 값은 비워 두고 기본값으로 채우지 않는다 |
| 조건 카드 검사 | `profile_check.py` | 고유번호 해석 실패·중복은 오류, 고시 11종에 없는 분류와 배점 합계 불일치는 경고, 비어 있는 조건은 "확인 필요" |
| 읽기 | `readers.py` | `.md`·`.txt`·`.docx`·`.hwpx`·`.pdf`를 자르지 않고 읽어 문단마다 제목 경로와 PDF 쪽을 남긴다. 웹 앱 첨부 추출은 파일당 12,000자에서 자르고 구조를 버려 쓰지 않았다. HWPX는 defusedxml로 읽고 압축 항목 수·크기를 제한한다 |
| 요구사항 | `requirements.py` | 영문 접두어형(`SFR-001`)과 고시 서식형(`기능요구사항-001`)을 찾는다. 접두어와 번호로 비교해 `SFR-1`과 `SFR-001`을 같게 본다. RFP 후보 탐색은 관행 접두어나 두 번 이상 나온 접두어만 남긴다(`ISO-9001` 같은 잡음 제외). 추적은 대응·누락·RFP에 없는 번호를 보고하고 대비표를 쓴다 |
| 조견표 | `crosswalk.py` | 평가항목마다 답하는 제목과 제출 PDF의 쪽. 표지 요약·목차·머리글에도 같은 제목이 나오므로, 원고에서 제목 바로 다음 본문 앞부분이 PDF에서도 뒤따르는 위치만 "본문 확인"으로 인정한다. PDF만 주면 목차로 보이는 쪽을 빼고 추정하며 "(확인 필요)"를 붙인다 |
| CLI | `scripts/publicdoc.py` | `text`, `scan-requirements`, `check-profile`, `trace`, `crosswalk --pdf`. 종료 코드 0 통과, 1 고칠 것, 2 입력 오류 |
| 안내 | `.claude/skills/public-sector-documents/SKILL.md`, `.agents/skills/public-sector-documents/SKILL.md` | RFP 읽기 → 조건 카드 → 원고 검사 순서와 규칙 |

**함께 고친 결함:** 작성 skill이 안내하는 작업 폴더 `work/`가 git 무시 대상이 아니었다. 고객 RFP나 원고가 commit될 수 있어 `.gitignore`에 추가하고 테스트로 고정했다.

## 6. 2단계 설계와 검증: 공공 표기 검사

`app/public_sector/notation.py`, `hangul_numbers.py`, CLI `notation <파일> --kind agency|submission`.

| 규칙 | 근거 | `agency`(행정기관 문서) | `submission`(제안서·보고서) |
|---|---|---|---|
| 항목 기호 순서(1. 가. 1) 가) (1) (가) ① ㉮), 단계 건너뛰기, 같은 단계 번호 끊김 | 시행규칙 제2조① | 오류 | 경고 |
| 날짜: 연·월·일 글자, `-`·`/` 구분, 마지막 온점 누락 | 규정 제7조⑤ | 오류 | 경고 |
| 시각: 오전·오후, "N시 M분" | 규정 제7조⑤ | 오류 | 경고 |
| 숫자 금액과 괄호 안 한글 금액 불일치 | 시행규칙 제2조② | 오류 | 오류(사실 불일치) |
| 숫자 금액 뒤 한글 금액 누락 | 시행규칙 제2조② | 오류 | 검사 안 함 |
| "끝" 또는 "이하 빈칸" | 시행규칙 제4조⑤ | 오류 | 검사 안 함 |

- 제목은 항목 순서를 새로 시작한다. 제목 자체가 항목 기호로 시작하면 그 단계에서 이어 간다.
- 같은 단계에서 1(첫 번호)로 돌아가는 것은 허용한다. 상위 항목이 바뀐 새 목록일 수 있어서다.
- 날짜의 온점 뒤 띄어쓰기는 조문에서 확인하지 못해 `2026.10.19.`와 `2026. 10. 19.`를 모두 허용한다. 시각은 분이 있거나 오전·오후가 붙은 경우만 본다(`24시각제` 같은 낱말 오탐 방지).
- 검사하지 않는 것: 들여쓰기(근거가 2012년 편람뿐), DOCX·HWPX 자동 번호 매기기로 만든 기호(본문 텍스트에 없음).
- 검증: `tests/test_public_sector_notation.py` 9건. 위반이 섞인 합성 공문은 규칙별로 9건을 보고하고, 같은 내용을 바르게 쓴 공문은 0건이다. 처음 구현에서 같은 단계 번호 끊김(나.→라.)을 놓치고 "오후 2시 30분"을 두 번 보고하던 결함을 이 사례로 찾아 고쳤다.

## 7. 3단계 설계와 검증: 과업 단계 문서 세트

`app/public_sector/report_types.py`, `reports.py`, CLI `report-types`, `report-skeleton --type <유형> --profile`, `report-check <파일> --type <유형> --profile`.

| 유형 id | 문서 | 섹션 근거 | 이행 대비표 상태값 |
|---|---|---|---|
| `execution_plan` | 사업수행계획서 | 공식 16개 목차(S7 별지 제5호) — 누락은 오류 | 계획, 협의 필요 |
| `start_report` | 착수보고서 | 관행 — 누락은 경고 | 계획, 협의 필요 |
| `interim_report` | 중간보고서 | 관행 | 완료, 진행 중, 미착수, 변경 |
| `completion_report` | 완료보고서 | 관행 | 완료, 미완료, 변경 |
| `policy_research` | 정책연구 결과보고서 | 관행(공통 기준 없음) | 없음 |
| `policy_research_moe` | 정책연구 결과보고서(교육부) | 초록·국문 색인어·영문 색인어는 공식(교육부훈령 제481호 별지 제7·8호), 초록 500자 내외(±30%, 공백 제외)는 경고 | 없음 |
| `business_plan` | 사업계획서 | 관행(공식 공통 양식 미확인) | 없음 |
| `feasibility_report` | 타당성 검토 보고서 | 관행(법정 예비타당성조사는 별도 지침) | 없음 |

- **섹션 인식:** 제목 앞 번호(Ⅰ., 1., 가., 제1장, 붙임 등)를 떼고, 제목이 섹션 이름이나 동의어로 시작할 때만 인정한다. 그래서 "품질관리 방안"은 "품질보증" 항목으로 인정하고, "주간 보고서 양식"은 "보고계획"으로 인정하지 않는다.
- **이행 대비표:** 조건 카드의 `tasks`(과업지시서 항목)와 `commitments`(제안서에서 약속한 인력·일정·산출물)를 함께 다룬다. 보고서의 표(Markdown·DOCX·HWPX 표 모두)에서 번호가 있는 행을 찾아 상태값을 확인한다. 행이 없거나 상태가 유형의 허용 값이 아니면 오류, "확인 필요"로 남으면 경고다. 이 표로 제안서 약속이 이후 보고서까지 이어지는지를 추적한다.
- **뼈대:** `report-skeleton`은 모든 섹션과 이행 대비표를 만든다. `[작성 필요]` 자리 표시가 남으면 `report-check`가 오류로 잡는다.
- **검증:** `tests/test_public_sector_reports.py` 12건. 8개 유형 모두 뼈대를 다시 읽었을 때 섹션을 빠짐없이 인식하고, 채운 중간보고서는 통과하며, 완료보고서의 잘못된 상태·누락 행·확인 필요가 각각 잡힌다.

| 검사 | 기준 | 판정 |
|---|---|---|
| 형식 | 조건 카드 `formats`(조달청 집행 건은 PDF, S9) | 허용 형식이 아니면 오류 |
| 전체 용량 | `max_total_mb`(조달청 집행 건 300MB, S9) | 넘으면 오류 |
| 별도 파일 | `separate_files`(예: 정량·정성·원가절감 제안서, S9) | 파일 이름에서 찾지 못하면 경고 |
| 쪽수 | `page_limit`, 이름에 "요약"이 있는 파일은 `summary_page_limit` | 넘으면 경고(표지·목차 포함 여부는 RFP마다 다름) |
| 블라인드 | `blind_evaluation`이 참일 때 본문, 파일 이름, 메타데이터(PDF 정보, DOCX `docProps`, HWPX 메타 파일)에서 식별 정보 검색 | 발견되면 오류. 식별 정보를 주지 않으면 검사하지 못했다는 오류 |

조건 카드에서 비어 있는 조건은 "확인 필요"로 보고하고 통과로 바꾸지 않는다. 검증: `tests/test_public_sector_submission.py` 4건(실제 PDF 출력, 작성자 메타데이터에 회사명을 넣은 DOCX 포함).

## 9. 통합 검증 (2026-10-20)

단위 테스트로 드러나지 않는 연결 문제를 찾기 위해 실제 사용 순서대로 전 과정을 돌렸다. 입력은 합성 자료다.

1. 합성 제안요청서를 HWPX로 만들었다(요구사항 총괄표·상세, 평가항목 배점표, 제출 조건, 잡음 `ISO-9001`).
2. 이 세션이 `text`·`scan-requirements`로 읽고 조건 카드를 썼다(`check-profile` 통과).
3. 기존 작성 경로(`proposal_kr`)로 제안서를 썼다. 실제로 생기는 실수를 일부러 넣었다: 교육 요구사항 누락, 오타 번호, 블라인드 평가인데 회사명 노출, 공공 표기와 다른 날짜.
4. DOCX·HWPX로 내보내고 PDF는 LibreOffice로 변환했다.
5. `trace`·`crosswalk --pdf`·`notation`·`submission`을 실행했다.

**결과:** 넣은 실수를 모두 잡았다.

| 검사 | 결과 |
|---|---|
| `trace` | 6건 중 5건 대응. 누락 `PSR-001`, RFP에 없는 `SFR-004` |
| `crosswalk --pdf` | 평가항목 4개의 목차 9개를 모두 본문 확인 쪽으로 채웠다(PDF 텍스트와 대조해 일치). "교육 및 지원"은 제안서에 섹션이 없다고 보고 |
| `notation` | 날짜 1건 경고, 오탐 없음 |
| `submission` | HWPX 형식 불허, 두 파일 본문의 회사명, 작성용 흔적(아래) |

**이 과정에서 고친 것**

- **요구사항 명칭 후보:** 표를 "라벨: 값 / 라벨: 값"으로 풀어 쓴 행에서 `/ 요구사항 명칭:` 라벨이 이름에 붙었다. 앞 구분 기호와 짧은 라벨을 떼고 다음 칸에서 끊는다.
- **여러 원고 파일:** 제안서 번들은 문서 4개를 따로 만든다. `trace`·`crosswalk`·`notation`이 원고 여러 개를 주어진 순서대로 한 문서로 읽는다(제출 PDF가 같은 순서로 합쳐진다).
- **조견표 본문 확인**
  - LibreOffice PDF는 목록 기호를 글머리 문자 줄로, 표를 칸별 줄로 바꾼다. 처음에는 9개 중 7개가 "확인 필요"였다. 비교를 글자·숫자만으로 하고 범위를 다섯 줄로 늘렸다.
  - 범위를 늘리자 목차 줄이 그 아래 본문을 끌어와 확인되는 퇴행이 생겼다. 원고의 다른 제목을 만나면 범위를 멈춘다.
  - 표 머리 칸이 대상 제목과 같은 경우(적용 기술)에는 멈추지 않는다.
- **작성용 흔적 검사(제출):** `proposal_kr` 번들은 문서마다 "PPT 구성 가이드" 섹션을 넣고, 작성 규칙은 근거 없는 값을 "확인 필요"로 둔다. 둘 다 제출본에 남으면 안 되므로 `[작성 필요]`, "확인 필요", "PPT 구성 가이드", TODO·TBD를 경고로 보고한다. "확인 필요"는 기능 이름 같은 정상 문장에도 나올 수 있어 오류가 아니다.
- **PDF 변환 엔진 오류(DecisionDoc 결함):**
  - 이 컴퓨터에서 Playwright 1.58.0이 쓰는 Chromium 빌드가 지워져 PDF 내보내기가 원인 설명 없는 500으로 실패했고, 작성 CLI는 traceback을 출력했다. 다른 프로젝트가 더 새 Playwright 브라우저를 설치하며 지운 것으로 보인다.
  - `build_pdf`가 엔진 시작 실패를 `PdfEngineUnavailableError`로 바꾸고, 전역 처리기가 `503 PDF_ENGINE_UNAVAILABLE`과 설치 명령으로 응답한다. 생성 결과 패키지 내보내기도 이 오류를 일반 변환 오류로 감싸지 않는다.
  - 작성 CLI는 실패한 형식만 기록하고 나머지 형식은 계속 만든 뒤 종료 코드 3과 원인을 출력한다.
  - 사용자 승인 뒤 `python3 -m playwright install chromium`으로 엔진을 복구했다. 복구 후 DecisionDoc 자체 PDF(Chromium)로도 조견표 9개 쪽이 모두 본문 확인이고 PDF 텍스트와 일치했다.
- **깨진 제출 파일:** 엔진 복구 뒤 처음 실행된 제출 검사 테스트에서, 작성용 흔적 검사가 깨진 파일 하나 때문에 전체 검사를 중단하는 결함이 드러났다. 읽지 못한 파일은 `unreadable_file` 오류로 한 번 보고하고 나머지 파일 검사는 계속한다. 각 파일 본문은 한 번만 읽어 블라인드·흔적 검사에 같이 쓴다.

**제품 관찰(고치지 않음):** `proposal_kr`의 목차는 고정이고 RFP 평가항목은 사업마다 다르다. 이번 RFP의 "교육 및 지원"에 해당하는 섹션이 번들에 없어 조견표가 빈칸이 됐다. 공공 제안서는 RFP가 지정한 목차와 평가항목을 따라야 하므로, 조건 카드의 평가항목에서 제안서 목차를 만드는 기능이 다음 후보다.

## 10. 한계

- 3·4단계의 관행 목차와 동의어는 합성 문서로만 확인했다. 실제 기관 양식과 다르면 유형 데이터에 동의어를 더한다.
- 블라인드 검사는 주어진 식별 정보 문자열만 찾는다. 로고 이미지와 간접 표현(대표 실적명 등)은 찾지 못한다.

- 요구사항이 고유번호 없이 문장으로만 적힌 RFP는 추적할 수 없다. 이때는 세션이 조건 카드에 번호를 붙여 쓰고, 원고에도 같은 번호를 적어야 한다.
- 대응 여부는 고유번호 언급으로 판단한다. 대응 내용이 요구사항을 실제로 충족하는지는 사람이 검토한다.
- 평가항목과 목차의 연결은 세션이 조건 카드에 적는다. 제목이 원고와 글자 단위로 다르면 찾지 못한다.
- PDF 텍스트 추출은 `pdfplumber`(선언된 의존성)를 쓰고, 없으면 PyMuPDF를 쓴다. 스캔 PDF는 읽지 못한다.
