## Clean-room design references

The following are independent DecisionDoc design references, informed by the
source review but not copied from any source implementation:

- structured skill metadata and explicit license/provenance fields;
- deterministic discovery and stable ordering;
- content hashes for change detection and review receipts;
- bounded filesystem discovery rather than unbounded recursive scanning;
- path-traversal and symlink checks before reading a discovered path;
- risk labels that make review and approval scope visible; and
- authority boundaries that separate discovery, presentation, approval, and any
  later execution or provider call.

These references do not authorize a new skill runtime. DecisionDoc must not
load third-party instructions into prompts, execute third-party scripts, or
adopt a third-party schema, class model, tool protocol, or provider integration.
The implemented registry uses DecisionDoc-native contracts and tests. Any
future source reuse must independently review the applicable license for every
source artifact.

## Rejected runtime and integration decision

DecisionDoc will not vendor or execute OpenAI, Anthropic, or Microsoft skill
implementations as part of this analysis. In particular, the Microsoft design
decision's filesystem discovery, progressive disclosure, resource loading, and
optional script execution are architectural observations only; they are not a
request to add a generic skill runtime here.

The implemented follow-up is a bounded DecisionDoc-owned metadata registry and
authenticated catalog with an explicit first-party root, deterministic
ordering, content hashes, path and symlink validation, risk labels, and a
non-executable default. The API exposes only native catalog metadata; it does
not expose instruction bodies or source paths. Provider calls, AWS resources,
training or dataset operations, deployment, publication, and external side
effects remain outside this scope.

DocumentOps execution now derives a DecisionDoc-native strict public binding
from that registry before a captured operation claim. The binding contains its
schema version, selected skill name/version, risk level, exact content SHA-256,
catalog fingerprint, and explicit false code-execution/external-runtime
authority; it contains neither the instruction body nor its source path. The
service includes the exact binding in canonical retry identity and passes it to
the Agent as the expected binding. The Agent re-resolves task compatibility and
catalog state before provider access, so unknown/unsupported skills and binding
drift fail closed. This remains a first-party prompt-selection contract, not a
generic skill loader or runtime.

## Verification and effect boundary

- The implemented follow-up is limited to a DecisionDoc-owned, first-party
  Markdown registry and authenticated read-only catalog. It loads no external
  instruction body, exposes no source path, executes no skill code, calls no
  provider, and persists no catalog state.
- Each discovered file is bounded to the first-party registry directory,
  symlinks and malformed metadata fail closed, and exact source bytes bind a
  per-skill SHA-256. Canonically sorted public metadata binds the deterministic
  catalog fingerprint.
- A successful Agent run uses one verified binding in its prompt, response,
  trajectory and captured replay result. Exact operation replay returns the
  original binding without another provider or usage call; selected-skill or
  catalog drift conflicts before execution. Authenticated run audit keeps only
  safe task/binding-hash/replay/false-authority provenance in addition to the
  generic HTTP audit envelope.
- The change adds no external runtime dependency, AWS resource, dataset upload,
  training path, deployment step, publication action, commit, or push.
- The 2026-08-12 focused local registry/Agent/API/operation-store/audit command
  completed with `143 passed`. Targeted `py_compile`, Ruff E/F/W, Bandit
  medium/high, secret hygiene, README metric, registry validation, and
  `git diff --check` gates also passed. This evidence is not live-provider, AWS,
  G2B stage, deployment, or production proof.
